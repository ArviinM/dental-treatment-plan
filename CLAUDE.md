# SIA Dental — Treatment Plan Generator

Generates branded treatment plan PDFs for **SIA Dental**, three clinics in Melbourne, Australia: Essendon, Burwood, Mulgrave.

**This has real users.** Ericka and her team use it in actual patient work. It is not a sandbox — a broken deploy means someone cannot give a patient their plan today. They are also **not technical people**, and often mid-appointment.

## The rules that override the others

**1. Do not change what the team already does.**

- The plan builder at `/legacy` is **frozen** — its layout, its Generator / Settings / About tabs, its instant canvas preview, its Import Plan and Download PDF buttons. Don't redesign it, don't "improve" it, don't add features to it.
- New capability goes on **new pages**, never as a replacement for something that works today.
- If a change removes something people could do before, **say so explicitly** rather than letting it land quietly. That is a decision for Arvin and Ericka, not an implementation detail.
- When in doubt between "cleaner" and "same as they're used to", pick same.

**2. Write for people who are not technical.**

- Labels say what you get, in words someone would say out loud: "Make a plan", not "Generator"; "History", not "Activity log".
- One action keeps **one name** everywhere — sidebar, page heading, button, toast. Two names for one thing is the main way this tool could get confusing.
- Never link somewhere unfinished without marking it "Soon" first. Nobody should land on an empty page wondering if they broke something.

**3. Patient data is regulated. Not by HIPAA.**

HIPAA is US law and does not apply. Victoria means the **Privacy Act 1988 (Cth)** and the **Health Records Act 2001 (Vic)** — and the Privacy Act's small-business exemption does *not* cover health service providers, so this practice is in scope regardless of size.

- **Never log patient data off the database.** `console.error`, Vercel function logs and any error reporting sit outside the access controls. Log identifiers and messages, never the request body.
- **Never put a patient name in a URL** — it reaches server logs and browser history. Ids in the path only.
- `activity_log` names patients by design, so it is patient data too, with the same retention and access rules as `treatment_plans`.
- No patient data in analytics or third-party tools.

## Stack

Next.js 16 (App Router, Turbopack) + React 19 + TypeScript, Tailwind v4, shadcn/ui, deployed on Vercel. Package manager is **yarn**: `yarn dev` (port 3000), `yarn build`, `yarn lint`.

**Who can change what.** Two roles. `staff` make treatment plans and can read
everything a plan needs — fees, dentists, templates. Only `admin` can change the
fee schedule, the dentist list, templates, layout settings or accounts, and only
admin sees History. Fees were staff-editable at first and were locked down on
2026-09-21 at Ericka's request. Every one of these is enforced in RLS, not just
hidden in the UI — a hidden button is not a permission.

**Supabase is live.** Project `SIA Dental`, region `ap-southeast-2` (Sydney), on
Arvin's dedicated SIA DENTAL org. 8 migrations applied and reference data seeded
as of 2026-09-17. `src/lib/database.types.ts` is generated — never hand-edit it,
run `yarn db:types`.

**Do not run `supabase start` / Docker on Arvin's machine without asking.** It
eats disk and he has had trouble with it. Work against the linked project.

## Gotchas

**PDF coordinates are bottom-left origin; canvas is top-left.** `CanvasPreview.tsx` converts with `height - (y * scale)`. Getting it backwards silently puts text off-page. Every position in `DEFAULT_TEMPLATE_SETTINGS` is PDF points from the bottom.

**Page size is 810 × 1440 pt** (11.25 × 20 in) — deliberately not A4 or Letter. It matches the Canva artwork. Don't "fix" it.

**Two renderers draw this document** — `lib/pdf/generate.ts` (pdf-lib, server) and `components/preview/CanvasPreview.tsx` (Canvas 2D, browser). Their measurements and colours come from **`src/lib/pdf/layout.ts`**. Put shared numbers there; never copy a value between the two files.

**`TreatmentPlanBlank.pdf` is one file, three pages**: 0 = cover, 1 = first treatment page, 2 = continuation. See `TEMPLATE_PAGE` in `layout.ts`.

**The dentist photo must be cropped before it reaches the server.** There is no `<canvas>` on the server; `lib/image/circle-crop.ts` does it in the browser and `generate.ts` expects a ready circular PNG data URL.

**Dentist photos live in Supabase Storage**, not in `public/`. `seed.sql` cannot
carry binary files, so `scripts/migrate-staff-photos.mjs --apply` is the other
half of that migration — it is idempotent and skips anyone who already has a
photo. The copies still in `public/dentist-photos/` are unused by the app.

**Templates are drafted, then published — never live on upload.** An upload
went live instantly once and broke every plan: the Canva master had its own
table and heading printed on it, so the app's were drawn on top. Uploads now
wait as drafts (`published_at` null) until an admin checks a sample plan and
publishes. `/api/templates/[id]/sample` renders one with the REAL renderer.

**The plan template must be artwork only.** The app draws the cover heading,
the patient's name and the treatment table. A design with those already printed
on it gets them twice. Team pages are appended whole and can contain anything.

**Every template falls back to the bundled original** if it is missing,
unreachable or will not open — see `loadWithFallback` in `lib/pdf/assets.ts`. A
plan must always be producible. "Use the original" in the UI does the same on
purpose.

**The canvas preview paints the LIVE artwork** from `template-previews`, made in
the browser at upload time (`lib/pdf/render-previews.ts`) because the server has
no canvas. It used to paint the bundled PNGs whatever was uploaded, which is
how a garbled PDF shipped behind a clean-looking preview. Any missing or failed
image falls back to the bundled one.

**Team pages are static PDFs** with staff baked into the artwork. Changing `data/dentists.ts` does **not** update them. Expect the directory and the team page to disagree.

**`pdfjs-dist` must stay lazily imported.** It touches `DOMMatrix` at module scope, which breaks the production build when a prerendered page can reach it. See `getPdfJs()` in `services/pdfParser.ts`.

**Generated PDFs often exceed 5 MB**, over most email attachment limits. The weight is in the template assets — `public/templates` alone is 28 MB — not the drawn content.

**Tests: `yarn test` (unit, safe) and `yarn test:integration` (REAL DATABASE).**
The integration suite creates and deletes real auth users and rows in the live
Supabase project. Everything it makes is tagged `zz-autotest` and removed in
afterAll, and it never deletes a row it did not create — but do not run it once
real patient records exist. Assertions are always made with a signed-in user's
client, never the service role: a service-role assertion passes no matter how
broken the policies are.

Also verify PDF changes by generating a real one. Use a plan long enough to paginate (>10 items) and spanning multiple phases/visits, so pagination and subtotal rows are exercised. `POST /api/plans/render` can be driven directly with curl.

**Lint is scoped, deliberately.** `eslint.config.mjs` downgrades some rules for the frozen legacy surface so working code is not churned to satisfy a linter. New code must satisfy them as errors — do not widen that list.

## Conventions

- **Schema changes are migrations**, never SQL run by hand against the database.
  `npx supabase migration new <name>`, then edit the generated file. The
  dashboard's SQL editor is for reading, not for changing things.
- Conventional commits: `feat:`, `fix:`, `refactor:`.
- **Never add AI attribution to commits or PRs** — no `Co-Authored-By`, no "Generated with". Every commit in this repo.
- Don't commit or push unless Arvin asks.
- Brand colours live in `lib/pdf/layout.ts` (`PALETTE`) and `globals.css`: SIA Teal `#2BBFB3`, SIA Purple `#A5338D`, Dark Gray `#1F2937`. Patient names render purple, doctor names black.
- Font is Nunito throughout, embedded into the PDF from `public/fonts/` via `@pdf-lib/fontkit`, with a Helvetica fallback.
